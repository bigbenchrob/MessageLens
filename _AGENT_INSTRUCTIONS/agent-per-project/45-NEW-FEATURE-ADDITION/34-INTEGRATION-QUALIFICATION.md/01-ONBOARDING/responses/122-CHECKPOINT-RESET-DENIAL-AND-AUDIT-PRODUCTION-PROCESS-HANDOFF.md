## Required finite lifecycle (proposal, not existing protocol)

1. **Owned → freezing:** accept one handoff request for the exact admitted process incarnation and jurisdiction occurrence. Reject duplicates/stale requests. Seal scheduling synchronously. Observable: local admission/epoch state; not exit.
2. **Freezing → drained or refused/unknown:** await applicable readers, import/build and preservation work through owners' explicit futures. Separate work futures from handoff futures to avoid recursive self-await. Settlement must include capability cleanup. A deadline produces a terminal handoff refusal/unknown while admission stays sealed; it cannot assert cancellation or release a still-live writer. No launch/exit on incomplete proof.
3. **Drained → target admitted or refused:** native owner validates the exact official bundle location and code identity against the admitted production context, excluding ambient/development/user-selected paths. Existing claim data is insufficient to establish this replacement-target contract. No persistent archive changes, permission prompts or reset as fallback. A target can change after validation; later launch binding/revalidation is part of the missing protocol.
4. **Target admitted → external handoff armed or refused:** a component surviving old-process death is necessary for exit-before-launch. Existing helper demonstrates only development spawning. There is no inspected production-ready helper/host protocol to adopt. Before allowing exit it must establish bounded launch responsibility, exact old incarnation, target binding and noninheritance of archive-lock authority. This is a requirement, not an assertion that an API already implements it.
5. **Armed → old exit proven or refused/unknown:** old process requests termination while still holding its lock; actual process death and relinquishment must be independently observed by the surviving component. Never unlock early. Launch-before-exit currently loses to older-app detection/lock contention. Same PID, PID reuse, permission failure during observation or ambiguous termination must not advance to successful handoff.
6. **Old exit proven → replacement launch requested → native admitted or failed/unknown:** use the bound target; new native startup independently claims its lock and validates identity/root. A launch request is not a lock/admission acknowledgment. An intervening duplicate may win; fail/report rather than launch repeatedly. Exact old/new incarnation linkage and acknowledgment are absent today.
7. **Native admitted → Dart admitted → freshly assessed → one selected owner:** recreate root authority/container and independently read all evidence. No old epochs, mutation capabilities or occurrence receipts cross the boundary. Failure remains refusal/diagnostic, never generic legacy App or a second poller. Production activation stays separately gated.

Failure rules: spawn/arming failure leaves the old process alive and sealed with a report; old process refusing exit prevents new writer admission; crash before arming means no promised relaunch; crash after arming needs independent observation, not optimistic success; launch failure after old death cannot be reported by the old UI and needs a bounded external report or next-launch diagnostic. Target refusal/no permission/identity change is terminal for that attempt. No infinite retry, deleting lock files, early unlock, broad root cleanup or data rollback. A hung drain remains UNKNOWN, even if an observer's `Future.timeout` fires. Actual OS exit, helper survival, lock-descriptor inheritance, LaunchServices behavior, target integrity and TCC/FDA continuity remain UNKNOWN without separately approved signed-runtime qualification.
